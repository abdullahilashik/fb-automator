Authentication

How the extension proves who the user is to DealerCore, obtains a Bearer token, and keeps that token alive — across two independent flows, one user-facing button.

Primary

Silent handshake

Reuses the web session cookie

Fallback

Interactive OAuth

Authorization Code + PKCE

Secret in bundle

None

Public client, PKCE only

Overview

Defined in utils/dealercore-config.js · implemented across utils/dealercore-api.js and entrypoints/dealercore-bridge.content.js

The extension never asks the user for a DealerCore password. Opening the sidepanel is usually enough — it reuses the session the browser already holds. When that is not possible it falls back to a visible OAuth round-trip, and only then does it need a click. Both flows converge on the same end state: a DealerCore Bearer token in extension storage, plus a cached session snapshot used purely for rendering the UI.

Concern Approach
Credentials in codeNo client_secret is bundled. Public client + PKCE.
Consent promptsFirst-party client in Nova bypasses the approval screen.
Multi-environmentTokens are keyed per origin, so dev and prod never collide.
Token theft via CSRFHandshake runs same-origin from a content script, so SameSite cookies are still attached.
Page context leakageInbound postMessage is origin- and source-validated.
Silent re-authEvery DealerCore page load retries the handshake, unless explicitly signed out.

Architecture

Four extension surfaces cooperate. Only the content scripts may talk to DealerCore with cookies.

content

dealercore-bridge

Injected on every DealerCore page. Owns the silent handshake, the STOCK_FOR_ADVERTISING listener, and answers DC_RUN_HANDSHAKE. Being same-origin is what makes the cookie flow work.

service

Routes NAVIGATE_TO_CREATE, TRIGGER_MARKETPLACE_SYNC and DEALERCORE_LOGOUT. Knows nothing about OAuth.

sidepanel

AuthModal

Renders the single login button and runs the decision chain. Holds no protocol logic of its own — it composes helpers from dealercore-api.js.

shared

dealercore-api.js

The protocol layer: PKCE generation, authorize URL, token exchange, authed fetch wrapper, session validation, sign-out. Every network call to DealerCore lives here.

Storage keys

All state is in browser.storage.local. The token is the single source of truth — the UI never keeps its own copy.

Key Purpose
token_<origin>The Bearer token, one entry per environment (token_https://dev.dealercore.com.au).
dealercore_base_urlActive origin. Re-derived from the active tab when that tab is a DealerCore page.
dealercore_sessionCached user / dealer / branch / branches / savedAt. UI convenience only — never used to authorise a request.
dealercore_signed_outBoolean latch. Blocks the automatic handshake after an explicit sign-out.
Why per-origin tokens? A single token key would let a dev token silently authorise requests against production. Keying by origin makes that class of bug impossible.

The login button

entrypoints/sidepanel/AuthModal.jsx → handleLogin() :65 · runOAuthFlow() :46 · handleTestFlowA() :108

There are two connect buttons, and the distinction matters. The landing page's Connect with DealerCore is the primary path: it skips straight to Flow A because auto-connect has already tried the silent handshake and come up empty. The chain below lives in the AuthModal, reachable from the avatar menu, and is what you get if you want the extension to choose. Choosing a strategy is the extension's job, not the user's.

1

Try the silent handshake

connectViaSession() — ensures a DealerCore tab exists, pings it for a handshake, and validates the result. Usually instant.

2

Fall back to interactive OAuth

runOAuthFlow() — only reached if step 1 throws. Opens the DealerCore login page and exchanges the returned code.

Both steps call the same finish() helper, so they are indistinguishable to the rest of the app — the UI only ever sees "connected". A handshake failure is logged to the console and surfaced as a neutral toast; it is never shown as an error, because it is an expected, handled transition.

Temporary

A second button, TEMP — Test Flow A, invokes runOAuthFlow() directly. It exists to exercise OAuth in isolation while the handshake keeps succeeding and short-circuiting the fallback. Remove it once Flow A is confirmed in CI or staging.

Flow B · Silent handshake

entrypoints/dealercore-bridge.content.js → silentHandshake() :13 · driven by utils/dealercore-api.js → connectViaSession() :243

Default path

The browser already holds a valid laravel_session cookie for DealerCore. The handshake trades that cookie for a scoped API token — no UI, no typing.

entrypoints/dealercore-bridge.content.js

// Fired on every DealerCore page load — never blocks rendering.
silentHandshake(baseUrl);

const res = await fetch(`${baseUrl}/api/v1/auth/handshake`, {
  method: 'POST',
  credentials: 'include',   // ← carries the session cookie
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(payload),   // {} by default
});

Why a content script and not the sidepanel

A fetch() issued from the extension's own page is cross-site. The session cookie is SameSite=Lax, so the browser withholds it and the endpoint answers 401. Running the identical request from a content script on a DealerCore page makes it same-origin, the cookie is attached, and it succeeds.

This is the single most important constraint in the whole integration, and it is why the handshake is not implemented in dealercore-api.js despite living alongside the other network helpers.

Triggering it on demand

A content script may not be injected yet when the user clicks, so connectViaSession() retries five times at 800 ms. If the tab reloaded mid-flight and the reply was lost, it falls back to checking storage directly before declaring failure. 

for (let attempt = 0; attempt < 5; attempt++) {
  try {
    result = await browser.tabs.sendMessage(tabId, { action: 'DC_RUN_HANDSHAKE' });
  } catch { result = null; }   // no receiver yet
  if (result?.ok) break;
  if (result?.unauthenticated) throw new Error('…log in to the main app, not /nova');
  await sleep(800);
}
Do not send client_id yet. The endpoint validates it as a first-party client and rejects the handshake until that flag is set. That couples the working default path to an unrelated server flag, so it is omitted by default. Flip HANDSHAKE_SEND_CLIENT_ID to true once the client is confirmed first-party.

Auto-connect on open

utils/dealercore-api.js → tryAutoConnect() :402 · handshakeFromExtension() :370 · connectViaSession() :280 · ensureBridgeInjected() :257 — entrypoints/sidepanel/Sidepanel.jsx :111

Opening the sidepanel attempts the handshake on its own. In the common case the user never touches a login button — the panel is simply already connected. There is no prerequisite tab to open first, and nothing is ever shown on screen.

Three strategies are tried in order, cheapest first:

  1. Reuse the stored token. Revalidated against /api/v1/auth/me, so a stale token can never read as a live session. A dead one falls through. Reported as via: 'existing-token'.
  2. Ask the server directly. handshakeFromExtension() posts to /api/v1/auth/handshake from the extension page itself with credentials: 'include'. No tab is borrowed, no content script is injected, no message round-trip. Reported as via: 'direct'.
  3. Borrow an open DealerCore tab. connectViaSession() drives the content-script bridge, injecting it first if the tab predates the extension load. Same-origin, so it still works if CORS is ever tightened server-side. Reported as via: 'handshake'.

It still refuses two things, because an automatic action that can interrupt someone is worse than one extra click:

  • It never falls back to OAuth. Auto-connect is handshake-only. A login window with no user action behind it is intrusive, so failure simply leaves the connect button visible.
  • It honours sign-out. If dealercore_signed_out is set, auto-connect returns immediately — signing out actually sticks.

Why the direct call is allowed at all

The bridge content script originally existed because a cross-site POST from an extension page would be dropped by SameSite rules. That is no longer the binding constraint. DealerCore answers credentialed cross-origin requests from the extension origin — verified against the running server, which echoes the origin with Access-Control-Allow-Credentials: true on both /api/v1/auth/handshake (preflight 204) and /api/v1/auth/me (which allows the authorization header). So Chrome attaches the existing session cookie and the exchange completes with no page involved.

credentials: 'include' is not optional here: omit it and Chrome strips the session cookie, producing a bare 401 that looks identical to being signed out. Strategy 3 is kept as a safety net precisely because this depends on server configuration rather than on the extension alone.

A bug that made this silently not work

Before the direct path existed, the only route was the content-script bridge — and the bridge is statically declared, so Chrome only injects it into pages loaded after the extension. Any DealerCore tab that was already open — the norm right after a reload, an update, or a fresh chrome://extensions load — had no listener, so sendMessage threw and the handshake had nowhere to run. The symptom was a four-second spinner followed by the connect button, with no error to explain it. Auto-connect looked implemented but was not.

ensureBridgeInjected() fixes the fallback path by injecting the bundle on demand via scripting.executeScript() on the first "no receiver" response, then retrying after 150 ms — 151 ms to connect instead of four seconds and a failure. The script path is read from the manifest rather than hardcoded, and the bridge guards itself with a window.__DC_BRIDGE_READY__ sentinel so injecting into an already-wired tab cannot double-register its listeners. When injection is genuinely refused — a restricted page, or a missing host permission — the loop gives up after one retry instead of spinning.

A stored token short-circuits the handshake, but it is revalidated against /api/v1/auth/me first, so a stale token can never be mistaken for a live session. A dead token falls through to a fresh handshake. 

export async function tryAutoConnect() {
  try {
    const { dealercore_signed_out: signedOut } = await browser.storage.local.get(['dealercore_signed_out']);
    if (signedOut) return { ok: false, reason: 'Signed out.' };

    const base = await getDealerCoreBaseUrl();
    const { token } = await getAccessToken(base);
    if (token) {
        try { // revalidate — a stale token is not a session
        const me = await fetchMe(base, token);
        await persistSessionSnapshot(base, me);
        return { ok: true, base, me, via: 'existing-token' };
      } catch {} // dead token → handshake below
    }

    // Preferred: no tab, no content script, no message round-trip.
    try {
      const { me } = await handshakeFromExtension(base);
      return { ok: true, base, me, via: 'direct' };
    } catch (directError) {
      // Same-origin fallback: borrow an open DealerCore tab.
      try {
        const { base: usedBase, me } = await connectViaSession({
          openTabIfMissing: false,
          focus: false,
        });
        return { ok: true, base: usedBase, me, via: 'handshake' };
      } catch {
        return { ok: false, reason: directError?.message };
      }
    }
  } catch (e) {
    return { ok: false, reason: e?.message || String(e) };
  }
}

The landing page renders exactly one of three states from a single status value, so there is no separate "connecting" screen that could flash and vanish. It never throws, so a failure can only ever move the page to idle.

  • connecting — set on open, and again for the duration of any connect attempt. Shows a spinner, an indeterminate progress bar and the current phase as subtext.
  • idle — the silent attempt found nothing to work with. Offers Connect with DealerCore. This is deliberately not an error state: having no DealerCore tab open is normal on a cold browser, and showing a red error for it would be alarming and wrong.
  • error — reserved for a real Flow A failure. Shows the server's actual message and a Try again button.

Pressing Connect with DealerCore goes straight to Flow A — it does not repeat the handshake, since auto-connect has already had its chance. The error text is rendered pre-wrap so the multi-line explainProbe() output stays readable. The AuthModal is a separate, unchanged entry point reachable from the avatar menu.

Flow A · Interactive OAuth

utils/dealercore-api.js → createPkce() :65 · buildAuthorizeUrl() :74 · launchOAuthLogin() :363 · surfaced by explainProbe() :139

Fallback path

Standard OAuth 2.0 Authorization Code grant with PKCE, opened through chrome.identity.launchWebAuthFlow(). Used when the user has no live DealerCore tab, or has deliberately signed out.

Step 1 — generate a PKCE pair

64 random bytes become the verifier; its SHA-256 digest is the challenge. The verifier never leaves memory and is never stored.

Step 2 — build the authorize URL

GET {BASE}/oauth/authorize
  ?client_id=9a5c8e32-2d14-41b9-8390-1c5c0a377755
  &redirect_uri=https://<runtime-extension-id>.chromiumapp.org/
  &response_type=code
  &code_challenge=<base64url(SHA256(verifier))>
  &code_challenge_method=S256

The redirect URI is derived at runtime from browser.runtime.id, so it always matches the installed extension rather than a hard-coded value.

PKCE is mandatory on this server. Omitting code_challenge returns 400 invalid_request. Note that the upstream auth-guide.md documents this URL without PKCE and with an empty scope= — following it literally fails even with a correctly registered client. scope is also omitted, because an empty value can be parsed as a scope literally named "".

Step 3 — pre-flight, then open the flow

Chrome collapses every failure into "Authorization page could not be loaded.", which hides the real cause. So the extension probes the same URL first with redirect: 'manual' and surfaces the genuine status instead of letting Chrome swallow it.

  • 302 → /login — healthy. The server wants the user to sign in.
  • 401 + invalid_client — client unknown, revoked, or not first-party.
  • 400 + invalid_request — a parameter is missing or malformed (usually PKCE).

Step 4 — exchange the code

POST {BASE}/oauth/token

{
  "grant_type": "authorization_code",
  "client_id": "9a5c8e32-2d14-41b9-8390-1c5c0a377755",
  "redirect_uri": "https://<id>.chromiumapp.org/",
  "code": "<authorization code>",
  "code_verifier": "<in-memory verifier>"
}

No client_secret is sent — the client is public, and the PKCE verifier is the sole proof of possession.

Step 5 — confirm identity

fetchMe() calls /api/v1/auth/me with the fresh token. A successful call is the real proof of validity; the code exchange alone is not trusted.

Token lifecycle

utils/dealercore-api.js → authed() :413 · getAccessToken() :35 · verifySession() :475

Every authenticated call funnels through one wrapper, which is why a dead token can never leak into the UI as a stale success.

async function authed(base, token, path, options = {}) {
  const res = await fetch(`${base}${path}`, { ...options, headers: {
    Accept: 'application/json',
    'Content-Type': 'application/json',
    Authorization: `Bearer ${token}`,
    ...options.headers,
  }});

  if (res.status === 401) {
    // Drop it so the UI falls back to the login button.
    await browser.storage.local.remove([tokenKeyFor(base)]);
    throw new Error('Unauthenticated (401). Please log in again.');
  }
  if (!res.ok) throw new Error(`DealerCore request failed (${res.status}).`);
  return res.json();
}

Self-healing also happens passively: because every DealerCore page load fires a handshake, a user who re-authenticates in the browser is picked up automatically the next time they visit the app — no extension interaction required.

Sign out

utils/dealercore-api.js → clearDealerCoreSession() :389 · triggered from Sidepanel.jsx → handleLogout() :184 · routed by background.js :37

Sign-out must work identically regardless of which flow authenticated the session, so it never inspects the UI's auth object.

  1. Remove every token_* key, not just the active origin — otherwise a stale dev token can silently reconnect after switching to prod.
  2. Remove dealercore_session and auth.
  3. Set dealercore_signed_out = true to latch the automatic handshake off.

Step 3 matters: without it, the very next DealerCore tab load would immediately mint a fresh token and the user could never actually sign out.

Developer guide

Edit utils/dealercore-config.js · declared in wxt.config.ts · verify with AuthModal.jsx → handleDiagnose() :133

Step 1 — Create the OAuth client in Nova

  1. Sign in to the DealerCore Nova admin panel (this is a separate app from the main DealerCore application).
  2. Go to Integrations → OAuth Clients and create a client.
  3. Set Redirect URIs to https://<extension-id>.chromiumapp.org/ — trailing slash included.
  4. Tick First Party. This sets first_party = true and is what bypasses the consent screen.
  5. Leave it public — no client secret.
  6. Copy the generated Client ID.
Pin your extension ID before you start. An unpacked extension without a manifest key derives its ID from the folder path, so moving or renaming the directory silently changes it and invalidates the registered redirect URI. Open chrome://extensions, copy the ID, and add a key to the manifest so it can never drift.

Step 2 — Point the extension at your environment

Edit utils/dealercore-config.js — the only file that needs changing per environment.

export const DEALERCORE_CONFIG = {
  CLIENT_ID: '9a5c8e32-2d14-41b9-8390-1c5c0a377755',
  DEFAULT_DOMAIN: 'https://dev.dealercore.com.au',  // origin only
  REDIRECT_PATH: '/',
  HANDSHAKE_SEND_CLIENT_ID: false,
  SCOPE: '',
};

Never append /nova — Nova is the admin panel and is not part of the runtime flow.

Step 3 — Build and load

npx wxt build

# or dev with hot reload
npx wxt

Load .output/chrome-mv3 as an unpacked extension via chrome://extensions → Load unpacked.

Step 4 — Verify the server before touching the UI

Confirm registration independently of the extension. This isolates server misconfiguration from extension bugs in one step.

Result Meaning

Step 5 — Smoke-test the landing page

  1. Silent path, tab open: sign in to the main DealerCore app, leave that tab open, then open the sidepanel. You should briefly see the spinner, then land straight on the listing view — no click, no popup.
  2. Silent path, no tab open: close every DealerCore tab, then open the sidepanel. It should connect anyway via the direct handshake. This is the case that previously fell back to the button.
  3. Stale extension reload: with a DealerCore tab open, hit reload on chrome://extensions, then reopen the sidepanel. The bridge is injected on demand, so this must still connect without you refreshing that tab.
  4. Not signed in: sign out of DealerCore in the browser, clear the extension's storage, open the sidepanel. The spinner should settle on Connect with DealerCore — and must not show an error.
  5. Flow A: press Connect with DealerCore. Expect the DealerCore sign-in page, then a successful token exchange.
  6. Flow A failure: sign in with bad credentials. Expect a red Couldn't connect panel with the server's own message and a Try again button.
  7. Reuse: close and reopen the panel. A stored token should be revalidated and reused, with dealer and branch still populated in the header and Settings.

To confirm the silent path is genuinely non-intrusive, watch for two things: no tab should open, and focus should never leave the tab you were using.

Server quirks

Observed against dev.dealercore.com.au · implemented in utils/dealercore-api.js → buildAuthorizeUrl() :74, probeAuthorize() :107 · contradicts auth-guide.md :151

Hard-won knowledge about this deployment. Each item was verified empirically.

Gotcha

The Accept header flips the result

/oauth/authorize returns 302 for any HTML-ish Accept but 401 for application/json. A healthy client therefore looks broken to any JSON-flavoured health check. Never probe this endpoint as JSON.

text/html,application/xhtml+xml302 → /login
full Chrome header302 → /login
application/json401

PKCE is mandatory

Omitting code_challenge yields 400 invalid_request. The upstream guide's authorize URL omits it — the doc is wrong, and following it literally breaks a correctly configured client.

The redirect URI trailing slash is significant

…/ and … are different registrations. Omitting the slash produces 401 invalid_client.

Distinguishing "unknown client" from "not first-party"

Both surface as 401 invalid_client. Send a deliberately invalid client ID as a control: if it also returns 401 invalid_client while the real one returns 400 or 302, the real client is registered and the problem is the first-party flag or its grants.

Confirming the client row exists

A POST /oauth/token with grant_type=client_credentials and no secret answers 400 unauthorized_client for a real public client, but 401 invalid_client for a nonexistent one. Useful when debugging server state without database access.
